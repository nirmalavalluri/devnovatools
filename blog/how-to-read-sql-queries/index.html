How to Read Any SQL Query in Plain English

📅 August 18, 2026⏱ 7 min read 🛠️ Try the SQL Query Explainer →

Every developer eventually inherits a SQL query they didn't write — in a code review, a slow-query log, or a database migration. This guide walks through reading any SQL query clause by clause, in the order the database actually runs it, so you can understand what a query does without guessing.

SQL Reads Top-to-Bottom, But Doesn't Run That Way

The biggest source of confusion when reading SQL is that the clauses are written in one order but executed in a different one. You write SELECT first, but the database evaluates it fifth. Once you know the real order, queries stop being a wall of keywords and start being a pipeline.

Written orderExecution orderWhat it does
1. SELECT5Choose which columns end up in the result
2. FROM1Pick the starting table(s)
3. JOIN2Combine rows from other tables
4. WHERE3Filter individual rows, before grouping
5. GROUP BY4Collapse rows into groups
6. HAVING6Filter groups, after grouping
7. ORDER BY7Sort the final result
8. LIMIT8Cut the result down to N rows

That's the single most useful fact for reading unfamiliar SQL: read FROM/JOIN first to see what data the query starts from, then WHERE to see what's filtered out, then GROUP BY/HAVING to see how it's summarized, and SELECT last to see what's actually returned.

A Worked Example

Here's a query that looks intimidating at a glance but is simple once you follow the execution order:

SELECT
  c.name,
  COUNT(o.id) AS order_count,
  SUM(o.total) AS lifetime_value
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'completed'
GROUP BY c.name
HAVING COUNT(o.id) >= 3
ORDER BY lifetime_value DESC
LIMIT 10;

Reading it in execution order:

  • FROM customers c — start with every row in customers
  • JOIN orders o ON o.customer_id = c.id — attach each customer's matching orders; a customer with no orders is dropped by this JOIN (that's what makes it an inner join, not a left join)
  • WHERE o.status = 'completed' — throw out any joined row where the order wasn't completed, before anything is grouped
  • GROUP BY c.name — collapse the remaining rows down to one row per customer name
  • HAVING COUNT(o.id) >= 3 — keep only customers with 3 or more completed orders (this has to be HAVING, not WHERE, because it depends on the COUNT, which only exists after grouping)
  • SELECT ... COUNT(o.id), SUM(o.total) — for each surviving group, compute the order count and total spend
  • ORDER BY lifetime_value DESC — sort the results, highest spender first
  • LIMIT 10 — keep only the top 10

In plain English: "Show me the top 10 customers by lifetime spend, among customers with at least 3 completed orders."

WHERE vs. HAVING — the Question That Trips Everyone Up

This is the single most common point of confusion in SQL:

  • WHERE filters individual rows, before grouping happens. It can't reference an aggregate like COUNT() or SUM(), because those don't exist yet at that point in execution.
  • HAVING filters groups, after grouping happens. It's the only place you can filter on an aggregate value.

Rule of thumb: if the condition mentions a raw column (status = 'completed'), it's a WHERE. If it mentions an aggregate function (COUNT(*) > 5), it's a HAVING.

Types of JOIN, at a Glance

JOIN typeReturns
INNER JOINOnly rows that match in both tables
LEFT JOINEvery row from the left table, matched data from the right (or NULL)
RIGHT JOINEvery row from the right table, matched data from the left (or NULL)
FULL OUTER JOINEvery row from both tables, matched where possible
CROSS JOINEvery combination of rows from both tables

When reading a query, a bare JOIN keyword means INNER JOIN — if it should include unmatched rows (e.g. "customers even if they have zero orders"), you'd expect to see LEFT JOIN instead.

Subqueries: A Query Inside a Query

A subquery is just a SELECT nested inside another statement. Read the innermost query first — it's evaluated first, and its result becomes an input to the outer query.

SELECT name FROM customers
WHERE id IN (
  SELECT customer_id FROM orders
  WHERE total > 1000
);

Read inside-out: "First, find every customer_id with an order over $1000. Then, find customer names matching those IDs."

CTEs (WITH clauses): Named Subqueries

A Common Table Expression (CTE) is a subquery given a name up front, so the main query reads more like plain English:

WITH big_spenders AS (
  SELECT customer_id, SUM(total) AS total_spent
  FROM orders
  GROUP BY customer_id
  HAVING SUM(total) > 1000
)
SELECT c.name, b.total_spent
FROM customers c
JOIN big_spenders b ON b.customer_id = c.id
ORDER BY b.total_spent DESC;

Read the WITH block first as its own self-contained query ("customers who've spent over $1000, and how much"), then read the main query as if big_spenders were a real table.

Window Functions: Aggregates That Don't Collapse Rows

Unlike GROUP BY, a window function computes an aggregate without reducing the number of rows — each row keeps its own identity but gains a calculated column:

SELECT
  name,
  department,
  salary,
  RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank
FROM employees;

The OVER (PARTITION BY department ...) part is the tell: "restart the ranking for each department." Every employee row is still returned — you just get their rank within their department attached to it.

A Fast Checklist for Reading Unfamiliar SQL

  1. Find FROM/JOIN first — what tables, and how are they connected?
  2. Check WHERE — what rows are excluded before anything else happens?
  3. Check GROUP BY — is the data being collapsed into summary rows?
  4. Check HAVING — is a filter applied to those summary rows?
  5. Read SELECT last — what columns, and what's calculated?
  6. Check ORDER BY and LIMIT — how is the result trimmed and sorted?
  7. If there's a subquery or CTE, isolate it and read it as its own standalone query first.

Frequently Asked Questions

Why does my query error when I use an aggregate in WHERE?
Because WHERE runs before grouping, so aggregates like COUNT() and SUM() don't exist yet at that stage. Move the condition to HAVING instead.

What's the difference between a subquery and a JOIN?
A JOIN combines columns from two tables into one row. A subquery in a WHERE clause (like WHERE id IN (...)) only uses the other table to filter rows — it doesn't add any of that table's columns to the result.

Does the order I write JOINs in matter?
For INNER JOINs, generally no — the result is the same either way. For LEFT/RIGHT JOINs, yes — which table is "left" and which is "right" determines which unmatched rows get kept.
